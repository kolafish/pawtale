# 回忆录访谈与成书协作架构

## 文档状态

本文是回忆录产品的主架构文档，统一定义事实来源、主题讲述、成书补全、客户端缓存、请求超时和 AI 模型上下文。实时语音协议见 `MEMOIR_VOICE_CHAT_ARCHITECTURE.md`，当前物理数据结构和编辑入口见 `MEMOIR_DATA_MODEL_AND_EDITING_GUIDE.md`。

## 一、事实与状态不变量

- 原始音频、VoiceUtterance、ASR 原文和历史 TranscriptVersion 是事实来源；
- 校正、摘要、审阅和正文是派生结果，不能反向改写原始来源；
- 一次连续讲述直接作为一个 Material，同一时刻只属于一个 Section；
- 调整结构时移动 SectionMaterial，不复制或拆散原始讲述；
- 收录、隐藏、隐私、删除、冲突确认和拒答由用户或确定性领域逻辑决定；
- SectionDigest、ChapterDigest 和 BookReview 可失效、可重新生成，不是第二套事实；
- 当前素材归属、当前问题、当前章节正文和当前全书正文各自只有一套规范状态；
- 后台整理和生成失败不得导致原始音频、转写或用户修改不可见。

## 二、产品边界

### 2.1 主题讲述

主题讲述帮助用户自然地继续说下去。系统读取当前对话、最近素材、小章节摘要、话题地图和用户偏好，让 LLM 从受控动作中选择下一步。

允许动作包括：

- 继续倾听；
- 顺着当前内容追问；
- 询问人物关系、原因或结果；
- 总结确认；
- 回到已有小章节；
- 提供一个新话题；
- 暂停或结束。

话题地图只记录某个方面是否出现过素材、相关 Material / Section，以及用户是否不愿讨论。它不要求用户完成固定人生目录，也不产生“全部讲完”的结论。

### 2.2 成书补全

成书补全回答一个问题：当前内容下一步做什么，才能形成用户可以通读和确认的正文？

系统在三个层级审阅：

- Section：一个小故事、人物片段、人生阶段或观点是否能够被理解；
- Chapter：小章节之间的顺序、重点、过渡、开头和结尾是否成立；
- Book：人生阶段、主要人物、主题、篇幅和跨章衔接是否存在明显问题。

不是所有问题都需要采访：

- 缺少用户掌握且明显影响理解的内容：补讲；
- 用户主动要求的内容取舍、事实冲突：用户确认；
- 已有素材足够，只需调整结构、去重或改写：编辑处理；
- 不影响理解的次要细节：不产生问题。

私人回忆录默认保留讲述者愿意讲出的内容，不按正规出版或公开传播标准审查。
普通经历、婚姻家庭、个人感受、亲友姓名和称呼、爱好不产生隐私追问。
小节、章节和全书审阅不把模型输出的 `privacy` 候选放入当前问题队列；历史问题
及用户的保留、匿名化或不收录决定仍保存在数据库中，历史记录可追溯。
隐私事项不阻止正文更新、章节确认、全书组装、阅读或导出；事实冲突沿用既有确认规则。
用户显式设置的素材、小节或章节不收录范围必须继续生效，AI 不得自行恢复或删除内容。
当前分享入口是限时的“分享给家人”，不增加逐项隐私审批；没有独立的公开发布流程。
未来若用户主动选择公开传播，明显敏感内容的提醒应集中、可选，并尊重已有决定。
规则更新提升三级审阅引擎版本，以及首页、书稿和章节工作区的本地缓存版本，
避免旧审阅结果或旧隐私阻塞提示继续进入当前流程。

## 三、共享数据

两条链共享同一条主干：

```text
AudioFile
  → VoiceSession
  → VoiceUtterance（Material）
  → SectionMaterial
  → Section
  → Chapter
  → Book
```

`VoiceUtterance` 是规范 Material 实体。原始音频、ASR、校正文和 TranscriptVersion 始终可追溯。

主题讲述额外维护：

- 话题地图；
- InterviewBrief；
- 策略决策与评价日志；
- 用户偏好和拒答记录。

成书补全额外维护：

- SectionDigest；
- ChapterDigest；
- BookReview；
- 少量当前 CompletionIssue；
- 完整章节草稿和全书版本。

## 四、小章节

### 4.1 Section 是核心叙事单元

一个 Section 应能被相对独立地理解。支持的初始类型：

- `event`：有过程或转折的具体事件；
- `life_fragment`：生活片段；
- `person_portrait`：围绕一个人的描写；
- `life_stage_summary`：人生阶段概述；
- `viewpoint_reflection`：观点、感受或反思。

类型只影响审阅重点，不是强制写作模板。

### 4.2 素材归属不变量

- 一条 Material 同一时刻只归属于一个 Section；
- 一次回答不能被拆开后穿插到多个位置；
- Material 的章节归属由所属 Section 推导；
- 调整归属时移动 SectionMaterial，不复制原始讲述；
- Section 可以移动、排序、合并、拆分、隐藏或归档；
- 任何结构调整都不能改写原始讲述。

### 4.3 初始整理

新素材到达后，整理器可以：

- 放入已有 Section；
- 放入最相关章节的“待归类素材”，等待用户选择小节；
- 识别明显重复，但不能自行删除用户内容。

## 五、分层语义摘要

### 5.1 SectionDigest

SectionDigest 读取有序 Material 和必要的当前正文，输出：

- 简短摘要；
- 当前表达重点；
- 已经讲清的内容；
- 最值得处理的少量问题；
- 对应 Material ID；
- 输入签名。

不同 Section 类型使用不同审阅维度。事件关注背景、过程、转折和影响；人物关注关系、特点和意义；观点关注触发背景和个人理解。

### 5.2 ChapterDigest

ChapterDigest 主要读取有序 SectionDigest，并按需读取原文，判断：

- 顺序和时间线；
- 重复与重点分散；
- 小章节之间的过渡；
- 开头和结尾；
- 背景、人物和指代是否清楚；
- 是否需要合并、拆分或移动 Section。

### 5.3 BookReview

BookReview 读取当前可读章节正文，ChapterDigest 作为辅助；输入签名绑定正文版本和哈希，判断：

- 人生阶段是否存在明显空白；
- 跨章内容是否重复或断裂；
- 重要人物是否突然出现或消失；
- 各阶段和主题篇幅是否失衡；
- 全书开头、结尾和主题线是否成立。

小程序发起 BookReview 生成时必须通过持久化后台任务执行。任务提交后立即返回，
按章节摘要准备、全书审阅和结果保存阶段记录进度；小程序退出后任务继续，
再次进入时按项目恢复当前任务并轮询，不依赖页面内存保存运行状态。

BookReview 的 `candidate_issues` 持久化关联章节和解决方式。`user_decision`
问题的文字回答保存在对应 CompletionIssue 的 `outcome_note`；全部必答问题处理后，
用户可以发起一次持久化“根据回答调整书稿”任务。任务按 issue fingerprint 找回
BookReview 中的关联章节，只允许改写这些章节中已有小节的正文，不得改变章节或
小节的顺序、收录状态、标题、数量及归属关系。任务生成新的 BookOutputVersion，
原书稿版本必须保留。

Digest 和 Review 都是可重新生成的派生数据，不是事实来源。

## 六、增量问题

SectionDigest 最多保留三个候选发现，并把可由现有素材解决的内容单列为编辑建议；候选发现不会直接进入用户问题队列。ChapterDigest 汇总全部 SectionDigest 后负责合并、筛选和升级，ChapterDigest 与 BookReview 不设业务问题配额，只保留彼此独立且确实需要用户处理的问题。问题优先级综合考虑：

- 是否影响读者理解；
- 是否关系到重要内容；
- 回答后能否明显改善章节；
- 当前是否适合询问；
- 是否已经问过、解决、跳过或拒绝。

CompletionIssue 只保存经过章节或全书审阅筛选、真正进入处理流程的问题，不保存小节候选池。至少记录：

- scope：chapter / book（历史 section 问题在迁移时关闭）；
- 对应对象；
- 自然语言问题；
- 内部原因和优先级；
- 处理方式：interview / manual_review；
- fingerprint；
- 状态和处理结果；
- 相关 Material；
- 创建时的输入签名。

用户回答后：

```text
回答成为普通 Material
  → 归入当前或新 Section
  → 更新 SectionDigest
  → 更新 ChapterDigest
  → 关闭已解决 Issue
  → 再选择下一个最有价值的问题
```

回答已经明确归入某个 Section 且现有章节正文具有小节快照时，先以素材变化确定需要更新的小节。编辑判断可为消重、承接或前后照应纳入确有关系的其他小节；未受影响的小节正文原样复用，最后原子保存一个新的完整章节版本。生成引擎升级或小节排序变化不能单独使所有素材未变的小节失去复用资格。用户改变全局润色等级或明确发起整章重写时，后台只对该次风格变更做一次范围内的润色，安全结果直接生效；后续新讲述仍走增量路径。

`manual_review` 的文字回答不是语音素材，不创建 VoiceUtterance。它作为用户明确提供的
事实或决定保存在 CompletionIssue 中，并通过全书回答应用任务进入派生的全书版本。
任务必须校验当前 BookReview 输入签名、回答签名、关联章节和模型返回的短引用；
未应用的文字回答会阻止普通全书组装，已应用版本在相同输入下不得被组装流程静默覆盖。
未回答的清晰度、关系、顺序和结构等编辑问题不阻止现有章节组成可阅读、可导出的全书；
隐私和事实冲突问题仍阻止受影响章节进入全书，直到用户作出决定。
后台启动时会重新排队旧规则遗漏了可读章节的已完成组书任务；若仅部分章节因隐私或事实冲突暂不收录，
其余章节组成可阅读、可导出的当前书稿，并向用户说明收录章节数。
仅因组书规则变化重排且章节草稿未变时，不重新发起 AI 全书审阅，以免未回答的决定被新审阅标为过期。

全书审阅必须先区分问题的解决方式：

- `new_material`：确实需要新的亲历事实，才进入语音补充并将回答归入明确 Section；
- `editorial_change`：书名、全书定位、章节顺序、合并删减、过渡和篇幅等编辑问题，只形成编辑建议或进入对应编辑入口，不创建语音素材；
- `user_decision`：隐私、事实冲突和内容是否收录等决定，要求用户直接确认，不通过语音回答。

进入单项语音补充页时，当前问题已经由 CompletionIssue 确定并直接展示。客户端不得再次调用模型改写首问或自动朗读；用户可以直接开始回答，避免把已知问题重复经过策略模型、访谈模型和 TTS。

模型需要选择章节、小节、素材或其他内部实体时，提示词只使用本次请求内的 `C1`、`S1`、`M1` 等短引用；服务端负责与 UUID 双向映射并在持久化前拒绝未知引用。数据库、API、任务断点和审计记录仍使用真实 UUID。
所有会直接展示给用户的模型文本必须在服务端把这些短引用还原为“第几章/小节＋标题”；短引用不得进入页面、导出或语音。

“不记得”“以后再说”“不愿讨论”和“已有其他素材回答”都是明确结果，不能通过换一种问法持续追问。

## 七、用户可见流程

小程序使用一个连续首页：问候之后先展示会随讲述成长的故事树 Hero，「讲个新故事」入口位于 Hero 内；
其后依次展示独立的「接着上次说」、紧凑主题列表和「我的书」。首页统一使用「主题 → 故事」口径，
主题行展示其故事数量，不展示素材数量；可继续补充的提示只保留在树的整体状态和对应主题行，
不再增加重复的页尾汇总卡。首页最多展示三个主题标签，不展开章节编号、小节、素材或系统进度；
右上角“设置”进入原“我的”页面。
阅读、编辑、素材与实时语音仍为独立页面。返回已有首页时优先退栈，保留滚动位置；旧故事页链接重定向到首页故事区域。
主要路径为：

```text
讲述保存
  → 后台整理素材与小节
  → 增量更新章节正文
  → 确定性组装可读书稿
  → 后台检查全书
  → 首页故事区域直接阅读，按需查看待确认事项
```

自动链路复用 EditingJob；`update_book_draft` 持久化章节子任务、书稿版本和审阅任务。
每个就绪章节即可参与组装，未决隐私/事实章节暂不入稿；检查失败不影响已保存草稿阅读。
安全的新章节稿直接成为当前稿，保留旧版本；已确认章节仍可自动更新，不把后台应用伪装成用户确认。仅在新增素材与用户手改小节冲突，或事实、隐私等事项尚待决定时，保留候选或要求用户处理。生成期间素材或正文基线变化时丢弃过期结果，由原任务链按最新输入重排。已人工编辑且无法可靠合并的全书正文不会被自动组装覆盖。

首页使用一次 `story-snapshot` 请求读取身份、最近讲述、树的导航计数、增长事件和后台状态，不拉取书稿正文与版本历史；`draft-progress`
只投影持久化任务，GET 不推进工作。首页可见且已有项目时由一个刷新定时器持续读取，隐藏时取消并使旧响应失效、返回时重读。
故事树组件只消费视图数据和发送操作事件，增长事件保留服务端 event ID 与新增/更新目标，展示页面不确认或重跑后台生成。
失败、待确认、本次无新增和部分可读有独立中文状态；付费请求结果未知时仅由显式重试继续。
章节工作台和补全页保留为人工编辑、必要补讲与问题处理入口，不再是得到草稿的必经步骤。

Section 在章节工作台内展示和调整，不额外增加必须经过的页面。

章节状态使用一个读模型推导：

- `not_started`：尚未整理；
- `preparing`：正在整理或生成；
- `needs_input`：需要补讲或确认一件事；
- `draft_ready`：当前正文已自动更新，可阅读或修改，无须确认才能生效；
- `confirmed`：用户曾明确确认当前版本；后续自动更新不沿用该确认标记；
- `failed`：本次处理失败，原始素材未丢失。

前台不展示 Digest、fingerprint、scope、置信度等后台术语。

### 单页首页的增长反馈

普通讲述结束时先停止录音和连接，并读取服务器 session；仅在 `stopped` 确认后返回原首页的故事区域。
保存失败或结果未知保留在讲述页，切入后台后的完成响应不触发导航。补充书稿问题仍返回原章节。

首页首次读取旧事件只显示静态状态；同一页面按用户、项目和 event ID 去重后才对新事件显示一次轻微动效。
账号变更清理观察状态，隐藏页面清理动画。刷新和返回设置页不主动滚动；
用户选择「看看变化」才定位对应主题。小节事件在首页标记其所属主题，具体小节仍在章节工作台查看。
新增主题/故事与已有故事的补充使用不同文案，更新不制造新节点。
「知道了」是唯一的事件确认动作。浏览树时底部的「继续讲述」复用首页的授权与开始流程。


## 八、LLM 与领域逻辑边界

LLM 可以：

- 决定素材适合哪个 Section；
- 建议新建、合并、拆分、移动 Section；
- 生成摘要和编辑建议；
- 判断下一步最值得问什么；
- 选择访谈策略动作；
- 根据允许素材生成候选正文。

确定性领域逻辑负责：

- project 和用户权限隔离；
- 原始素材不可变；
- 一条 Material 只有一个当前 Section；
- 用户收录、隐私、拒答和删除决定；
- 输入签名、过期结果和并发发布；
- 正文 Material allowlist；
- 章节确认和全书组装条件。

LLM 不能：

- 创造用户没有讲过的事实；
- 把模糊记忆写成确定事实；
- 自动解决内容冲突；
- 覆盖用户排除或隐私决定；
- 删除素材；
- 因固定模板缺项而强制追问。

## 九、客户端数据与一致性

后端数据库始终是事实源；本地缓存只是按用户和项目隔离、可丢弃的完整展示快照。

- 已访问页面可以先展示缓存并后台刷新；
- 缓存信封包含 schema version、cached_at、scope 和 payload；
- 删除字段、修改类型或改变业务语义时提升缓存 schema，不能宽泛合并未知旧数据；
- 写操作先提交服务端，再更新或精确失效缓存；
- 请求超时或断网时写结果属于未知，先查询服务端状态，不能直接重发；
- 较早的响应不能覆盖较新的刷新或用户写入；
- 项目级 server revision 只用于快照刷新，不替代实体版本、事务或任务状态；
- `401` 只允许一次重新认证和一次原请求重试，`403` 不触发重新登录。

## 十、请求、任务与模型上下文

小程序 HTTP 使用共享 profile：

| Profile | 客户端上限 | 适用范围 |
| --- | ---: | --- |
| `telemetry` | 8 秒 | 不阻塞用户操作、失败可丢弃或稍后补发的审计事件 |
| `interactive` | 30 秒 | 普通读取和状态查询 |
| `mutation` | 60 秒 | 保存、移动、确认和任务创建 |
| `generation` | 10 分钟 | 暂时仍为同步协议的生成操作 |

后端文本模型使用共享 profile：

| Profile | Provider 上限 | 适用范围 |
| --- | ---: | --- |
| `realtime` | 15 秒 | 实时访谈策略等快速决策 |
| `interactive` | 60 秒 | 搜索解析、标题和轻量归类 |
| `generation` | 180 秒 | 摘要、审阅、规划和正文生成步骤 |

业务页面和业务 service 只选择 profile，不复制秒数。ASR、TTS、图片、上传下载和 WebSocket 的独立协议时限集中在对应 transport 或 provider 配置中。

后台和传输使用以下全局截止时间：

| 操作 | 上限 | 超时处理 |
| --- | ---: | --- |
| 通用编辑任务 | 60 分钟 | 取消当前步骤，任务失败落库，保留已提交检查点，用户可重试或续跑 |
| 分享视频任务 | 30 分钟 | 取消渲染与心跳，清理未完成文件，失败落库，不自动重复付费生成 |
| 书稿导出渲染 | 4 分钟 | 返回明确的 `504`；不修改书稿，后续请求复用仍在生成或已缓存的文件 |
| 小程序普通媒体传输 | 1 分钟 | 显示下载或上传失败，允许用户重试 |
| 小程序书稿导出传输 | 5 分钟 | 覆盖后端渲染和下载，显示明确失败 |

这些数值只定义在后端 Settings 或小程序 transport；业务代码不得另写毫秒数。任务租约只是防止多个 worker 同时执行，心跳续租不能绕过任务总截止时间。

超时层级满足：

```text
provider deadline < backend operation deadline < proxy deadline < client deadline
```

成本高、耗时长、分多阶段或不能安全重试的操作必须使用可恢复任务：

```text
创建任务
  → 返回 job ID
  → 持久化阶段和进度
  → 客户端轮询或订阅
  → 页面恢复时继续查询
```

Provider 超时表示结果未知，不能因为客户端没有收到结果就自动重复付费调用。只有确定请求未被接受或业务明确幂等时才允许自动重试。多阶段生成每完成一个昂贵步骤立即提交，后续失败只重做失败步骤。

章节检查和章节正文生成共用一个可恢复任务。检查按小节和整章报告阶段；正文严格按当前 Section 顺序逐节调用模型，每节成功后持久化正文、素材引用和输入签名检查点。失败后只有在输入签名、模型和操作类型都未变化时才能续跑，已完成小节不再调用模型；任务状态接口不向客户端返回检查点正文。

书稿导出先通过 `/book-output/export/info` 校验权限并获取固定版本、文件名、缓存签名和已生成状态。

PDF 的整理日期绑定书稿版本日期，文件名使用书名、阅读版/打印版和版本号。
`/book-output/export` 复用持久化文件，以进程间文件锁合并相同生成，完整结果原子落盘。

### AI 操作反馈分级

模型调用不统一显示虚构的百分比，而是统一按操作形态选择反馈。发起长任务的操作区域必须直接显示任务状态；如果任务转交给统一后台记录，发起位置必须保留明确的交接说明和查看入口。页面顶部或列表摘要可以重复显示同一任务，但不能成为唯一且不可发现的进度入口。

| 反馈级别 | 当前操作 | 页面反馈 | 进度规则 |
| --- | --- | --- | --- |
| 实时流 | 实时 ASR、访谈回复 LLM、流式 TTS | 录音、识别、思考、播放等当前阶段，以及实时文字或播放时间轴 | 不显示任务百分比；以真实事件和流式结果反馈 |
| 单次交互 | 语音搜索解析、章节规划、章名/书名建议、单小节 AI 修改、素材语音编辑预览、说话人逐句校对、章节与书稿朗读 TTS | 操作位置的加载态和明确阶段文案；成功后直接展示结果或进入播放时间轴 | Provider 未提供进度时不伪造进度条 |
| 可恢复任务 | 章节检查与逐节正文生成、小节重新分组、离线 ASR、素材插图、分享视频、成书编辑文案 | 持久化任务状态、阶段文案、可恢复轮询；可安全停止后续步骤时提供取消 | 有真实总量时显示完成数和确定进度；单次 Provider 阶段只显示不确定进度 |
| 后台派生 | 转写校正后的素材整理、主题图刷新、Digest、BookReview、访谈策略影子评估 | 原操作先确认保存成功；后台结果进入对应读模型、自动处理记录或错误状态 | 不阻塞前台，不展示与用户当前操作无关的进度 |

确定进度只允许来自服务端持久化的真实计数，例如已检查小节数、已生成小节数、已处理素材字符数或已完成批次。排队、整章判断、单次模型请求和最终保存没有可观测总量时使用不确定进度，不把预估耗时换算为百分比。任务失败时展示已保存的检查点；取消只停止后续步骤，不回滚已经安全提交的结果。

章节工作台同时在“本章进度”和实际发起正文生成的“本章正文”区域展示同一份任务状态。用户滚动到长页面下方后仍能看到当前小节、完成数和取消入口，不需要返回页首寻找进度。

全书批量检查必须由服务端批次聚合章节任务，客户端不能自行循环提交后把内存状态当作全书任务。批次持久化目标章节和子任务 ID，以已经进入终态的章节数作为唯一确定进度；页面重开后读取当前批次继续轮询。批次进入终态时还要冻结逐章结果，避免后续复用章节任务反向改写旧批次。部分失败或用户停止时保留已完成章节；重试请求必须携带来源批次，只把该批次未成功的章节放入新批次。

用户选择的模型沿完整链路传递：

```text
用户选择
  → 客户端 ai_model
  → API schema
  → workflow / job payload
  → AI factory
  → provider
```

生成和失败记录至少保存 requested model、resolved model、provider、timeout、elapsed 和 error type。结构化输出额外记录 finish reason 和响应长度，但不持久化包含用户素材的原始响应。
