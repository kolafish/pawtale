# 回忆录客户端数据与请求架构

## 文档状态

本文定义回忆录小程序的本地缓存、服务端数据一致性、认证请求、超时和 AI 模型选择边界。它与以下文档共同构成回忆录产品约束：

- `MEMOIR_NARRATIVE_ARCHITECTURE.md`：事实来源和成书质量；
- `MEMOIR_VOICE_CHAT_ARCHITECTURE.md`：实时语音状态机；
- `MEMOIR_INTERVIEW_AND_BOOK_ARCHITECTURE.md`：访谈与成书协作。

后端数据库始终是规范事实来源。客户端缓存是可丢弃的展示快照，不能成为事实、任务状态或用户修改的唯一保存位置。

## 一、读取与缓存

### 1.1 用户体验

已访问过的页面采用 stale-while-revalidate：

1. 校验并展示当前用户、当前项目下的本地快照；
2. 在后台向服务端读取最新快照；
3. 仅当响应仍属于当前用户、项目和本次加载序列时更新页面；
4. 服务端版本较新时替换本地缓存；
5. 无缓存时才显示完整的首次加载状态。

后台刷新失败时可以继续展示明确标记为旧数据的完整快照，但不能把部分失败响应写成完整缓存。

### 1.2 缓存作用域

每份业务缓存至少由以下信息定位：

- storage owner / user ID；
- project ID；
- resource type；
- resource ID（存在章节、会话等子资源时）。

登出、账号变化和项目切换不得读取其他作用域的数据。清理缓存时只清理明确作用域，不能依赖模糊的全局对象合并。

### 1.3 缓存信封

持久化业务缓存统一包含：

```text
cache_schema_version
server_revision
cached_at
scope
payload
```

- `cache_schema_version` 描述本地序列化结构；
- `server_revision` 描述服务端业务内容版本；
- `cached_at` 只决定是否需要后台刷新，不能证明内容仍是最新；
- `scope` 防止跨用户、跨项目读取；
- `payload` 必须是一个可独立展示的完整快照。

新增可选服务端字段通常不要求迁移。删除字段、修改类型或改变业务语义时必须提升 `cache_schema_version`。旧缓存只有在迁移简单、确定且无损时才迁移，否则直接丢弃并重新读取。

### 1.4 写操作

默认写入顺序：

```text
服务端提交成功
  → 使用响应更新相关缓存，或精确标记相关缓存失效
  → 更新页面
  → 必要时后台刷新关联快照
```

除非某个交互单独设计了回滚协议，否则不能先把用户修改只写入本地缓存。生成任务超时或网络断开时，结果属于“未知”，客户端应查询任务状态，不能直接重发并制造重复结果。

### 1.5 并发一致性

- 页面加载必须记录加载序列或请求令牌；
- 较早发出的响应不能覆盖较晚完成的刷新或用户写操作；
- 服务端 `server_revision` 小于当前缓存版本的响应不得落盘；
- 聚合快照应来自服务端的一致读取边界，客户端不拼接不同时间点的部分结果作为新快照。

## 二、服务端数据版本

服务端为项目级读取快照提供单调递增的 `server_revision`。任何会改变首页、书稿、章节工作台可见内容的已提交事务，都必须推进相应项目版本。

项目级版本用于判断是否需要重新取得快照，不替代数据库事务、实体版本或生成任务状态。章节编辑仍应使用实体版本防止并发覆盖。

聚合读取接口优先返回一个页面所需的完整读模型，避免客户端逐章读取和自行组装：

- 首页快照；
- 书稿首页快照；
- 章节工作台快照。

## 三、认证请求

会话 Cookie 是签名且有期限的凭据。客户端存在 Cookie 时直接发业务请求，服务端业务接口负责验证用户，不在每个业务请求前额外调用 `/api/auth/me`。

当业务接口返回 `401` 时：

1. 清除失效 Cookie；
2. 只执行一次适用的重新认证；
3. 认证成功后只重试原请求一次；
4. 仍失败则把真实认证错误交给页面处理。

`403` 表示当前身份无权访问目标资源，不能通过清理会话或重试掩盖。

并发请求需要认证时共享同一个认证 Promise，避免并发登录。

## 四、超时

HTTP 请求按操作语义选择统一 profile：

| Profile | 当前客户端上限 | 适用范围 |
| --- | ---: | --- |
| `interactive` | 30 秒 | 普通 GET、状态读取、轻量查询 |
| `mutation` | 60 秒 | 不调用长时 provider 的保存、确认、移动、任务创建 |
| `generation` | 10 分钟 | 暂时仍为同步协议的 LLM、ASR、TTS、导出等长操作 |

业务 service 使用 profile，不自行复制毫秒数。上传、下载、WebSocket 和实时音频拥有独立协议状态机，但其超时也应集中在各自 transport 层。

超时层级必须允许内层先返回有意义的错误：

```text
provider deadline < backend operation deadline < proxy deadline < client deadline
```

预计超过普通交互时限、成本较高或不可安全重试的生成操作，应使用：

```text
创建任务
  → 返回 job ID
  → 客户端轮询或订阅
  → 页面恢复时继续查询
```

提高前端超时时间只能保护仍采用同步协议的已有操作，不能代替任务化和根因调查。

## 五、AI 模型上下文

所有由用户触发的 AI 操作必须形成同一条模型上下文：

```text
用户选择
  → 小程序请求 ai_model
  → API schema
  → workflow/service
  → AI factory
  → provider
```

客户端 AI HTTP 请求统一通过 AI 请求入口补齐 `ai_model` 并选择生成超时。异步任务创建可以使用普通 mutation 超时，但任务 payload 必须持久化模型。

后端 AI factory 记录：

- requested model；
- resolved model；
- provider/service。

默认模型只用于请求确实没有模型上下文的后台任务。不得因为某一层忘记传参而静默改用另一个模型；新增 AI 入口时必须检查整条调用链。

## 六、可观测性与测试

诊断性能时区分：

- 客户端缓存命中和后台刷新；
- HTTP 往返数量；
- 数据库查询；
- provider 执行；
- 任务排队；
- 实际请求模型和解析后的 provider 模型。

测试保持小而直接，覆盖本次改动的用户可见行为、持久化/API 边界和真实回归风险。不为文档规则本身增加静态扫描、源码正则或枚举所有未来字段和模型的测试。
