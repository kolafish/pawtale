# 回忆录实时语音架构

## 文档状态

本文定义回忆录小程序实时语音链路：

- VAD 与录音控制；
- Streaming ASR；
- LLM 动态回应与追问；
- Streaming TTS；
- voice session、消息和转写的持久化；
- 自由讲述、主题讲述和成书补讲共用的语音状态机。

素材、Section、章节正文、缓存、请求和成书补全边界统一见
`MEMOIR_INTERVIEW_AND_BOOK_ARCHITECTURE.md`。

## 一、产品形态

用户面对的是一次自然语音访谈：

```text
VoiceSession
  → 实时录音
  → Streaming ASR partial
  → ASR final
  → VoiceUtterance（Material）
  → LLM 选择受控策略动作
  → Streaming TTS 回应
  → 下一轮或结束
```

系统支持三种讲述方式，名称和说明统一来自 `memoir-narration-mode.ts`：

| 讲述方式 | 用户怎么使用 | guidance_mode | interview_type | session_goal |
| --- | --- | --- | --- | --- |
| AI 访谈 | 想讲什么就讲什么，AI 听着；一段讲完了陪着想下一个话题 | guided_interview | ai_interview | open_narration |
| 书稿补充 | 先选待补问题，再围绕该问题补讲 | guided_interview | ai_interview | book_completion |
| 真人访谈 | 家人朋友提问，分别记录采访者和讲述者 | free_narration | human_interview | open_narration |

原来的“自由讲述”和“引导访谈”已合并为 AI 访谈，不再让用户选择。新的普通 AI 访谈在创建校验前
统一为 `guided_interview`，包括省略该字段或旧客户端显式传入 `free_narration` 的请求；真人访谈仍为
`free_narration`，书稿补充继续校验问题目标。历史普通 AI 会话读取、恢复和继续讲述时保留原始值，
展示、提问能力与新 AI 会话一致；加载中禁用和同一来源去重仍生效。真人访谈不生成 AI 回复，纯听写不受影响。
`interview_type` 表达谁来访谈，`session_goal` 表达业务目标。

自然语言搜索使用 `narration_mode=ai_interview / human_interview / book_completion`。AI 访谈（包括旧称
自由讲述、引导访谈、主题访谈）检索两种底层 guidance 值的普通 AI 会话，排除真人与书稿补充；
原有列表参数 `guidance_mode` 仍按存储值精确筛选。
可选访谈策略的 active/shadow 开关继续默认关闭。开启后，新旧普通 AI 会话均可获得话题候选；历史会话
接受话题后从原有素材 `framework_item_id` 读取当前话题，不改写旧模式、不放宽会话锚点数据库约束。

三种讲述方式都是回忆录级默认设置，在“我的回忆录”的编辑设置页统一修改。
首页不提供临时切换，开始时读取当前回忆录保存的 `guidance_mode`、`interview_type` 与
`session_goal` 默认值。书稿补充会先进入待补问题列表，选择问题后再创建补讲会话。
开始后只在标题位置展示本次方式，不提供展开或切换入口；准备、录音、AI 回应、大字模式和保存阶段
始终沿用服务端会话字段。修改回忆录默认设置只影响之后创建的新会话，不追溯当前或历史会话。
真人转写复用普通内容区域，不用全屏层遮住方式；章节补讲的返回关系不变。

## 二、核心持久化

实时链第一层只写：

```text
audio_files
memoir_voice_sessions
memoir_chat_messages
memoir_voice_utterances
memoir_transcript_versions
```

其中：

- AudioFile 保存原始音频资产；
- VoiceSession 保存一次访谈的目标、模式和生命周期；
- ChatMessage 保存用户与 AI 的对话顺序；
- VoiceUtterance 保存一次完整用户讲述，并直接承担 Material 角色；
- TranscriptVersion 保存 ASR 原文、自动校正和人工修改的可追溯版本。

ASR partial 只用于实时显示，不作为事实落库。只有 provider final 或明确的恢复结果
才能创建用户消息、VoiceUtterance、TranscriptVersion 和音频引用。

一次讲述保持完整，不在语音层拆成多条 Claim，也不在语音层决定正文位置。

`audio.end` 携带本轮客户端 `speech_detected`（可缺省）；仅在 ASR 正常排空后处理无文字音频。
有任何已识别文字时文字优先，包括末次 final 为空而之前 partial 有文字的情况。无文字且客户端未检测到活动时，
原音频与会话关联仍保留，结果记为 `empty`。端侧音量判断不能证明完全无声，因此不按时长丢弃录音；讲述列表默认折叠这类录音并显示数量，展开后仍可试听、重新识别。过滤在后端分页前执行，`empty_count` 与当前筛选范围一致；API 的 `include_empty` 默认 true 以保留已有调用语义。检测到活动或旧客户端未提供活动结果时记为
`unrecognized`，展示明确的未识别结果并允许听原声、重新识别。异常、断线、超时仍保存为可恢复的
`pending_transcription`，不能按空录音隐藏。每轮结束立即落定自己的音频，避免空白轮的缓冲混入下一段。

保存无文字音频时先记录当时的 completion_issue_id / framework_item_id，不把空录音当作已回答。恢复文字时只使用录音已有的归属完成补全，不读取会话后来切换到的新目标；无法恢复原归属的旧记录保留文字和原音频，不猜测关联。

补转写正常完成但没有文字时也落为 `unrecognized`；不会无限显示等待，更不会据此删除疑似方言、轻声等录音。
首页续讲提示与视频素材列表只读取有文字的来源；普通讲述记录保留不确定录音的恢复入口。
没有改变活动检测阈值；无文字且无音频的 `empty` 不可恢复。列表和详情使用同一恢复状态展示，不自动重试或重复收费；真实麦克风/噪声的判断仍需真机验收。


## 三、会话状态

双向 TTS 在首段可朗读文字到达后才获取 provider 并发名额、建立连接和启动合成超时。
LLM 首段文字和后续文字停顿使用 realtime 超时（默认 15 秒），整段生成使用 interactive 总时限（默认 60 秒），
包含等待 provider 并发名额的时间。HTTP/SSE 心跳和 usage 事件不能延长文字等待；这些时限不延伸到消费者处理文字的任务。
超时或客户端退出时立即关闭上游连接、释放并发名额，不在后台继续生成以等待 usage；仅对已经收到的用量计费，未知用量不估算扣费。
上游失败通过 `turn.failed` 提示稍等重试；保留已有讲述，丢弃未完成的 AI 回应，不自动开麦。默认模型不变，不自动切换模型。

访谈文字与朗读分别完成。TTS provider 明确返回不可用/超时（502/503/504）时发送 `audio.failed`，
继续等待并校验完整 LLM 文字，成功后按正常消息落库，`turn.completed.audio_status=failed`。
失败前的部分音频不作为完整朗读保存。小程序停止剩余音频播放，保留问题文字和重播/手动回答入口，
不会把失败朗读标为已播报，也不会自动开麦或结束会话。LLM 失败、用户取消及连接中断仍遵循原有失败/取消路径。
录音时保留上一句问题；补全成书复用已有的问题卡，避免重复展示。所有音色的访谈者都自称“小余”。

VoiceSession 使用明确状态：

```text
created → listening ↔ speaking → stopped
                    ↘ failed
```

客户端同时维护有限的瞬时状态：

- WebSocket 连接状态；
- 录音器状态；
- ASR partial；
- 当前 assistant turn；
- TTS 播放队列；
- 自动续听计数；
- 页面是否可见。

这些状态是可以重叠的独立事实，不合并成一个覆盖所有组合的大枚举。例如流式 TTS 已经
开始播放时，assistant turn 仍可能尚未结束。页面不能分别在标题、正文和操作区解释这些
布尔值，而必须通过一个纯派生的交互阶段统一决定当前视觉焦点：录音优先，其次是已经有
内容的 assistant 回应，再其次才是尚未产出新问题的讲述整理。交互阶段不单独持久化，
避免它与连接、录音、assistant 和播放的真实状态产生双向同步。

错误也按责任边界保留：assistant 文字失败与 TTS 播放失败是不同结果；TTS 失败不能抹掉
已经完成的文字。状态文案只由交互阶段和错误派生，不能反过来作为流程判断条件。

持久状态以后端为准。页面恢复、前后台切换或断线重连时，客户端重新读取
VoiceSession 和消息，不根据客户端缓存的 UI 状态猜测服务端结果。

首页保存当前 VoiceSession 的入口参数，实时状态由 voice-session 组件实例持有。首页刷新
不会重建正在展示的组件；用户点“首页”或“结束讲述”时，组件复用同一收尾流程，结束
streaming 并等待后端会话确认为 stopped 后才收起和刷新首页。收尾失败时留在讲述界面明确
提示；连接已断开时，读取后端会话，非终态会话复用 REST stop 主动结束并重新确认结果，无需重新开麦。
REST stop 要求该会话的 gateway 租约已释放；讲述中会话还必须具有本轮音频成功落库后写入的断线确认。
重新开麦清除旧断线确认，已结束的会话不能再次开麦；缺少本轮确认时（包括进程重启后）保持待确认，
不根据本地 client 已清空或服务端状态被 REST 写成 stopped 推断音频已保存。
gateway 收尾保存失败时回滚失败事务、保留待恢复原音频并记录 failed，再释放租约；客户端进入异常记录核对，不能显示保存成功。
不引入可恢复的隐式“暂停”状态。完成事件携带 session id，旧实例事件不能结束
下一次讲述。账号或项目改变时清除旧入口并卸载组件。

组件卸载后保留其失效标记直到实例被回收，迟到的授权或会话响应不能重新连接。
普通续讲和话题讲述通过用户、项目隔离的导航目标回到首页；章节补讲仍返回原章节。
首页嵌入时由首页刷新故事进度，组件不再重复轮询进度通知。

## 四、录音与 Streaming ASR

### 4.1 开始录音

开始前依次确认：

1. 当前页面仍有效；
2. 用户已完成语音授权和微信隐私授权；
3. VoiceSession 未停止；
4. gateway 已连接或可重新连接；
5. 当前 assistant 播放已停止或被用户打断。

录音帧通过 WebSocket 发送，客户端 VAD 只负责音量展示和自动收尾建议，不替代
provider final。

### 4.2 最终结果

收到 ASR final 后：

1. 服务端保存音频；
2. 创建或更新 ChatMessage；
3. 创建 VoiceUtterance；
4. 创建 TranscriptVersion；
5. 返回稳定 ID；
6. 再进入 assistant turn。

同一 provider final 必须幂等，重连或重复事件不能创建两份 Material。

### 4.3 恢复

如果音频已保存但转写未完成，记录页只展示“等待转写”，允许用户显式恢复。恢复流程
不能伪造空文本，也不能把失败吞成成功。

### 4.4 语音编辑命令

故事、小节和讲述文字的语音编辑复用同一个 `voice-text-editor` 和临时 dictation gateway，
不为首次修改、已有方案反馈或不同页面分别维护录音状态机。状态归属固定如下：

| 层级 | 唯一职责 |
| --- | --- |
| 页面 | 加载、AI 任务、修改方案等业务状态 |
| `voice-text-editor` | `idle / connecting / listening / stopping` 交互阶段 |
| Streaming ASR 客户端 | WebSocket、原生录音器和 ASR 协议事实 |
| 后端 gateway | `ready / listening / finishing / stopped / failed` 协议生命周期 |

页面不能复制连接或录音状态，也不能为同一个可见编辑流程交替挂载多个语音编辑器。
页面恢复已有方案时，先完成业务状态读取，再挂载唯一的编辑器；首次修改和继续调整只改变
文案、提交目标和 busy 状态。所有 Streaming ASR gateway 必须先释放用户容量租约，再发送
`session.stopped`，使客户端收到停止确认后可以安全进入下一次编辑或访谈。

短语音输入只有两种产品模式，但共用上述状态机：编辑命令进入页面后自动收音、停顿后自动
提交；需要逐项核对的补全回答只把语音转成文字，由用户确认后保存。模式由组件属性决定，
页面不得据此复制连接、录音、收尾状态。连续访谈仍统一复用 `voice-session`；它保留 TTS、
打断、持久化会话等正交事实，但连接过程只以 `VoiceChatConnectionStatus` 为唯一事实源，
不再另设与 `status === "connecting"` 重复的布尔状态。

语音编辑已确定要移动的完整小节时，预览只列出来源章节、小节标题和建议的新章名；
用户点确认按钮后才执行。模型不得把确认或未指定章名本身当作需要再次语音回答的歧义。

## 五、LLM 策略层

LLM 接收经过整理的 InterviewBrief，而不是直接读取所有数据库表。Brief 可以包含：

- 最近对话；
- 最近 Material；
- 当前 Section 摘要；
- 话题地图相关项；
- 当前 CompletionIssue；
- conversation momentum；
- 用户偏好与拒答记录；
- 安全约束；
- 本轮可用的候选动作。

候选动作由系统限制，例如：

- 继续倾听；
- 沿当前内容追问；
- 询问人物关系；
- 询问原因或结果；
- 总结确认；
- 回到已有 Section；
- 提供新话题；
- 暂停或结束。

模型选择动作并生成自然回应，领域逻辑决定动作是否允许。模型不能确认事实、改变隐私
决定、删除素材、覆盖用户排除项或自动解决矛盾。

策略决策记录输入快照、候选动作、选中动作、原因、生成问题、用户结果、policy version
和可选人工评价。日志用于 prompt 评估，不成为业务事实。

## 六、Assistant Turn 与 TTS

模型在同一次流式生成中先给出会话动作（`listen / pause / end`），再输出口语正文。服务端按明确的首部协议解析动作；首部跨 chunk 时先缓存，只有正文进入 TTS、`text.delta` 和 ChatMessage。缺失或非法动作让本轮显式失败，不再默认自动收音。旧的 JSON/纯文本猜测路径已删除。

旧实验策略中按关键词得出的暂停动作仅保留为建议，不再强制口语收尾；会话控制只有上述语义动作一个执行来源。

动作以用户对本次对话的最新意图为准：故事讲完、换话题、引用别人告别、否定结束与改口继续都不等于结束访谈。动作与 `expects_answer` 一起进入最终事件和消息元数据。客户端等音频播放结束后，`listen` 复用自动收音，`pause` 停止自动收音并保留手动继续入口，`end` 复用 `finishSession` 完成保存和退出。播放失败、被打断或页面失效时不自动退出；保存结果未确认仍停留原界面。重播暂停/结束回应不会重新收音或再次退出。

assistant turn 通过单一流返回：

```text
turn.started
text.delta*
audio.format
audio.frame*
audio.done
turn.completed
```

失败或取消使用：

```text
turn.failed
turn.cancelled
```

`turn.completed` 是本轮 AI 消息完成的唯一成功信号。客户端不能把 text delta 或部分音频
当作完整消息。模型漏写会话动作而返回正常口语时，保留同一轮文字和音频，按 `pause`
等待用户主动继续，并记录协议遗漏日志；不从告别措辞猜测自动结束，也不自动恢复录音。
不完整控制标记、未知标记或结构化输出仍作为协议错误处理，不能读进 TTS。

首次问候、欢迎回来、项目进度和访谈问题都作为同一轮结构化上下文交给 LLM，由一次文字
生成统一组织，再进入同一条 TTS 流；服务端不先播放固定进度前缀再拼接模型问题。语音
自动播报只读取尚未播放的 automation event，不把每轮实时计算的项目快照直接当作新
消息；讲述数量到达里程碑时写入一条语音专用 event，客户端播放成功后用现有
`voice-played` 回执消费。用户主动重听已保存消息不属于新的自动播报。

用户点击麦克风时可以打断正在生成或播放的 AI：

1. 客户端立即停止本地播放；
2. 发送取消原因；
3. 后端停止 LLM/TTS；
4. 中断的半句话不进入后续对话上下文；
5. 录音器开始接收用户讲话。

自动打断复用已认证的语音 gateway。小程序发送 `barge_in.start/frame/stop`（含
`monitor_id`），音频格式仍为 16 kHz、单声道 PCM16；监听帧不送 ASR，也不写入音频证据。
ECS 后端加载随代码固定、校验 SHA256 的 Silero ONNX 模型，共享权重，每次监听独立
维护模型状态。前 640 ms 标定当前播放音量，之后连续 160 ms 的人声概率 ≥ 0.8 且音量
超过播放基线时发送 `barge_in.speech`。音量门槛只用于播放回声标定，不再使用固定
0.035/0.07 响度门槛或 450/700 ms 发声等待。

小程序保留最近 2 秒监听音频。服务器返回讲话起点（含 160 ms 前置音频），客户端裁掉
更早的播放内容，立即取消 AI，并在授权同步期间继续缓存。正式录音复用同一个录音器，
先发送 `session.start`，再按顺序补送缓存和后续音频，不停止再重开麦克风。旧 monitor
事件不能触发新播放；检测响应过晚而起点已不在缓存中、准备超过 10 秒、后台退出或
授权失败时，明确停止/提示，不发送缺失句首的缓存。

该播放基线不是声学回声消除：首次标定期内的讲话、外放音量改变、强回声和小声插话
仍需要真机验证。真实往返延迟也会增加打断时间，160 ms 是模型确认窗口，不是总延迟。
模型固定在 `backend/app/services/asr/models/`，在现有后端进程内使用 CPU 推理，无需
额外服务、端口或云端模型 API；启动失败或模型校验失败会阻止后端启动。

TTS 播放失败不能删除已经完成的文字回复，但必须显式展示播放失败，并允许用户重听。

## 七、AI 访谈

AI 访谈给 AI 的上下文（`voice_interviewer_prompt.py`）：

| 上下文 | 开场 | 讲述中 |
|---|---|---|
| 本次会话最近 12 条对话 | 有 | 有 |
| 本次及以前会话的资料问答原文（仍需补问时，合计最多 7 组） | 有 | 有 |
| 以前讲过的相关原文（记忆激活） | 不检索 | 不检索（只有书稿补充检索） |
| 讲述者资料：称呼、性别、年龄、家乡 | 有 | 有 |
| 书稿概况：章节名和每章讲述段数 | 有 | 有 |
| 人生话题 | 讲得最少的 3 项和说明（第一次开场除外） | 一行列出各项和三档状态 |
| 上次讲到的章节 | 有 | 无 |
| 进度事实 | 有未播报的新进展时 | 无 |

讲述中 AI 主要是听众：叙述者还在讲（话没说完、故事没讲完）时，只用一句话接住，请他接着说，
不另起问题；一件事讲完了、说记不清了，或者问讲什么好，可以从人生话题里提一个可以拒绝的新方向；
叙述者说想自己讲、不想被问时，这次后面只接住。离线对比见
`/mnt/project-files/interview-question-review/离线对比结果.md` 第 4 轮。

开场按书的阶段决定：是否讲过按整本书判断，不再区分旧的自由讲述/引导访谈模式。首次和返回开场共用资料候选及已答/拒答排除规则，
只在欢迎语上区分；资料候选为空时邀请讲一件自己想讲的往事，不再用老家或成长地点绕过提问上限；
以前讲过且符合资料补问条件时，欢迎回来后先补问；否则给两个具体方向，一个接着上次，一个是还没聊的话题；从“讲述进度”页某个话题进入时，
从那个话题开头。叙述者明确换方向时，以他最新一句为准，不再用关键词识别。

首页「讲个新故事」复用会话已有的 `miniprogram_home` / `miniprogram_home_launch` 入口标记。
需要收集基础资料时仍走上述资料规则；否则只简短欢迎并邀请用户自己开启一件新故事，不推荐旧章节补充问题、
不要求接着上次讲，也不替用户选择话题。无指定话题的新故事开场在 active/shadow 策略候选中也不授权自动选题；
用户之后主动请求方向时仍可推荐话题。实际开始讲述后的自然追问复用原有流程；「接着上次」和主动补讲入口保持各自语义。

人生话题是一条按人生先后排的时间线（家世与出身、童年、求学与少年、工作与闯荡、成家与儿女、如今的生活、想留下的话）。

新书没有资料表单，讲述者资料在这本书的“资料会话”里用说话补上。资料会话是讲述者在这本书里第一次开口的 AI 访谈会话，
前提是这本书以前没有任何讲述（不分模式）；它在第一段讲述入库的同一事务里记到资料的 `profile_session_id`。
空会话、真人访谈（两个人的话都记在叙述者名下）、已有讲述的旧书都不会成为资料会话。
首场提前结束时，下一场讲述继续补问；首场和当前场之外已有用户讲述时，不再主动问资料。
未开口就退出的会话也计入实际提问次数。AI 访谈中的新讲述仍会采集资料；真人访谈和成书补访不采集。

问：资料会话里，代码按称呼、年龄、老家、性别的顺序选出候选及一个备选：还没有值、没说不想说，
称呼、年龄和老家跨会话问过不到两次，性别问过不到一次。
AI 排除最近对话中已经答了或拒绝了、但后台尚未写入的项，只问剩下的第一项，最多问一项。
只回答称呼后优先问年纪；一件事讲完时才补问资料，故事未完不打断，刚说了称呼就用称呼叫他一声。
接话消息照常入库，不等额外调用；带问号的那句入库后在接话流程之外用一次小模型判断实际问到了哪一项
（模型调用失败时按明确的问法判断），结果写进这条消息的 `metadata_json.profile_asked`。
判断结果出来之前，每个候选项先预留一次提问，判断结束后仅保留实际问到的项，因此判断再慢也每项最多问两次。
旧消息的单项 `profile_question` 仍计入次数。
本次对话取最近 12 条；仍有资料待补问时，另附本次及以前会话合计最多 7 组实际资料提问及完整回答，
不让后来的故事或未回答的开场挤掉这些回答。原文仅用于判断资料是否已答或拒绝，不代替数据库资料。
无应答重听或暂停提示不替换原问题：历史问答、续问选题和资料提取均保留同会话最近的实质提问；真正换题时才切断旧关联。
首次/返回开场和后续回合共用此判断，覆盖一次回答多项、同会话早期回答超出 12 条窗口、提取仍在排队，以及拒绝后再进入的情形。

读：任何 AI 普通访谈里讲述者每段话（一次录音）入库时，只要有空缺资料或讲述中采集的值，
就在同一事务里排一个后台任务（`narrator_profile.py`），
按录音段去重，绑定这段的转写版本和它之前的那句 AI 的话。任务读“已记下的资料 + 那句 AI + 这一段完整转写”，
提取这段支持的称呼、性别、年龄、老家（与已知值相同也照填），以及他这段明确不想说的项（记在 `declined_in`，之后不再问）。
写入前确认转写版本没变；值只能被同一段或更晚创建的录音段改掉，跨会话也按录音段创建时间排序，
来源（录音段、转写版本、轮次）记在 `inferred_from`；
重读时，当前录音段自己提供的旧值不放进“已记下的资料”，避免过期值影响重读。null 只表示本段不支持该字段，不能表示“与已知值相同”。
重读结果替换该录音段拥有的资料和拒答：不再得到支持的值及其来源、拒答标记会撤回；
仍有效的值更新到当前转写版本。其他来源及手动保存值保留，拒答来源按录音创建时间更新，旧录音重读不能撤回更晚的拒答。
若撤回称呼，只有仍等于该称呼自动书名的标题才恢复为「我的回忆录」，自定义书名保留。
来源录音段已删除时，采集值仍可被之后读取的讲述纠正，不会因此变成手动保存的值。
用户在回忆录设置里保存过的从不覆盖。任务先等待该段转写校正结束，校正失败或跳过时保留读取原文的路径。转写校正（包括已经归章的段落）、人工修改、离线重识别会换版本；资料与人物阅读的版本 2 检查点记录规范化源文本哈希，相同文字只重绑当前来源版本，实质文字变化才重新读取。旧检查点只在原转写版本匹配时复用。
停止追问不影响读，所以晚回答、结束前最后一段都会被记下。读的过程中换了版本，这次任务按成功收尾，
让队列接着跑新版本；读失败时任务自己在 30 秒、2 分钟、10 分钟后重试，三次都失败才标为失败。
失败时如果这段已经有新版本在排队，就按成功收尾让新版本带着新的重试次数去跑。
书名还是首页自动建书的「我的回忆录」时，按称呼改成「某某的回忆录」。首页书名下方一行小字显示这些资料，点开即回忆录设置。

讲述中途不播报进度；进度事件留到下一次开场。

话题地图不要求用户逐项填满。每个话题只统计置信度不低于 0.6 的主要匹配（或人工关联），
按讲述段数分三档：还没聊（0）、聊过一点（1–2）、聊了不少（3 段及以上）。

## 八、成书补讲

成书补讲复用同一 voice-session 组件和 assistant turn，只额外绑定：

- `session_goal = book_completion`；
- 当前 CompletionIssue；
- 目标 Section / Chapter；
- 问题创建时的输入签名。

一次只处理一个问题。用户完成有效回答后：

1. 回答保存为普通 VoiceUtterance；
2. 整理器把完整 Material 放入一个 Section；
3. 更新相关 Digest；
4. Issue 标记为已回答并重新评估；
5. 本轮语音结束，不自动追加细节题；
6. 用户回到章节工作台生成或更新完整章节正文。

用户选择“不记得”“以后再说”或“不愿讨论”时，本轮立即结束并记录明确结果，不能继续
换一种问法追问。

## 九、与成书链路的边界

语音层只产出可追溯 Material。成书链路是：

```text
VoiceUtterance
  → SectionMaterial
  → Section
  → SectionDigest
  → ChapterDigest
  → CompletionIssue / 完整章节正文
  → BookOutput
```

归属和正文生成不在 WebSocket 回调里同步执行，而通过独立领域服务和 Job 完成。失败时
原始音频和转写仍然可见。

结构调整统一在书稿的章节/Section 工作区完成，避免多个页面同时修改素材归属。

### 回想与明确暂停

访谈会话动作以讲述者的当前意图为准：边讲边找词、说“我想想”仍保持 listen；明确要求暂停收音或暂时离开才返回 pause，结束本次讲述才返回 end。引用故事中其他人的话不操作当前会话。小程序录音中的主按钮“讲完这段，请小余接话”表示提交当前轮并让访谈员回应，不表示结束整个会话；结束沿用保存离开。

当前录音结束仍由现有静音分段状态机负责。提示词离线对照未证明能稳定避免故事中途插话，因此不以调整静音阈值或后处理文本替代会话时序修复；静默倾听和自然抢话仍待单独验证。
