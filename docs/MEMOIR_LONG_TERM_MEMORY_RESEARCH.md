## 一、调研目标与初步结论

本轮调研重点回答四个问题：

1. 长期记忆如何从持续对话中提取，才能尽量准确又不过度模板化；
2. 记忆应如何保存，才能处理来源、版本、时间、冲突和用户纠正；
3. 记忆应如何检索，才能兼顾姓名、地点等精确词和不同说法下的语义相关性；
4. 检索出的记忆应在什么情况下被激活并提供给模型，而不是无差别地塞入上下文。

初步结论是：

> “老余口述”的长期记忆不应是一份不断覆盖的用户总摘要，也不能只是历史对话的向量索引。更合适的是一套以原始讲述为证据源、分阶段提炼、混合检索、谨慎激活的分层系统。

对回忆录而言，错误地记住一个人物、时间或关系，会直接损害讲述者对 AI 的信任。因此早期实现应优先优化记忆精确率、来源可追溯和不乱覆盖；没有提取到的内容仍可从原始素材重新发现，而被错误激活的“事实”可能主动误导后续访谈和自动编辑。

## 二、代表性系统调研

### 2.1 Codex Memory：两阶段提取与渐进式读取

Codex 当前开源实现把记忆生成拆成两个后台阶段：

1. **单会话提取**：从已经结束、空闲时间足够且符合条件的会话中筛选与记忆有关的内容，由模型生成结构化的 `raw_memory`、`rollout_summary` 和可选 slug；
2. **全局整合**：从多次单会话结果中选出仍有价值的输入，增量更新全局记忆文件，并处理新增、修改和删除。

值得注意的设计包括：

- 提取任务允许 `succeeded_no_output`，即一次有效处理可以明确得出“没有值得长期保存的内容”；
- 提取提示词强调用户原话、结果状态、可复用知识和证据，不鼓励把探索性讨论、助手建议或一次性印象升级成长期记忆；
- 原始会话证据保持不变，整合层通过增量 diff 更新，不直接改写原始会话；
- 记忆读取启用时，`memory_summary.md` 是始终注入上下文的紧凑导航层；
- `MEMORY.md` 是可搜索的手册层；
- 只有需要精确细节时才继续下钻到单会话摘要或原始 rollout；
- 当前本地读取实现以导航摘要和字符串/关键词搜索为主，不依赖向量数据库。

这套设计说明，长期记忆不一定从“给所有历史做向量检索”开始。一个小而稳定的导航层，加上可追溯的详细层和原始证据层，也可以形成有效的渐进式记忆读取。

对“老余口述”最有价值的启示是：

- 一次访谈结束后先形成会话级候选，再跨会话整合，不在实时对话主链路中仓促改写全局记忆；
- 允许本次没有长期记忆，防止为了产出而产出；
- 把“人物和故事导航”与“详细事实和证据”分开；
- 用户的明确表达应高于助手转述和模型推断；
- 对尚未讲完、结果不确定或只处于讨论状态的内容，保留其认识状态，不压缩成确定事实。

### 2.2 DeepSeek Harness：会话历史基础设施不等于长期语义记忆

截至本次调研使用的 DeepSeek Harness 源码快照，其原生能力主要是：

- 以追加式 `SessionEvent` 日志作为会话事实源；
- 通过 JSONL 或 SQLite 持久化完整事件流；
- 对模型当前可见上下文进行压缩，同时仍在日志中保留被替换事件及压缩记录；
- 使用 SQLite 全文索引跨会话搜索事件；
- 显式读取其他会话或引用受限的会话上下文快照。

这些能力解决的是“历史能否持久化、回放、压缩和精确查找”，还没有自动完成以下长期记忆工作：

- 从讲述中提炼稳定人物、事件和关系；
- 判断两条说法是重复、补充还是矛盾；
- 形成跨会话的用户画像或故事地图；
- 根据当前任务自动激活高价值长期记忆。

DeepSeek Harness 官方仓库提供 Memorix、MCP Reference Memory 和 Engram 三种第三方记忆 MCP 的参考配置，但全部默认关闭，且官方明确说明它们只是互操作示例。没有加载这些配置时，Harness 自身不内建长期语义记忆服务。

对“老余口述”最重要的启示是：

- 原始会话/音频历史和派生长期记忆必须分层；
- 压缩摘要只能服务于上下文窗口，不能取代可回放的原始证据；
- 精确全文检索仍然有价值，特别适合姓名、地名、方言、称谓和稀有关键词；
- 长期记忆、向量索引和人物关系图都应视为可重新生成的派生层，不能成为唯一事实源。

主要来源（源码快照 `b150a551b8d465e31e418e1b2eaf5e79bbb7d28e`）：

### 2.3 Mem0：从覆盖式更新演进到 ADD-only 与多信号检索

Mem0 早期论文和旧版实现采用的典型流程是：

1. 从新对话提取事实；
2. 用向量搜索找到相近的旧记忆；
3. 让模型对每条候选决定 `ADD / UPDATE / DELETE / NONE`；
4. 将最终记忆存入向量库并保留操作历史。

当前主线实现已经转向 ADD-only 提取：

- 单次 LLM 调用从新消息中提取独立、可理解的记忆；
- 相关旧记忆主要用于语义去重和建立 `linked_memory_ids`；
- 新记忆不会在自动提取阶段直接覆盖或删除旧记忆；
- 精确文本 hash 用于拦截完全重复；
- 实体从记忆文本中抽取，并关联回相应记忆。

当前开源检索会组合：

- 向量语义相似度；
- BM25 关键词得分；
- 查询实体与记忆实体之间的关联加权；
- 可选的后续 reranker。

Mem0 托管版公开材料还描述了写入时的时间推理和基于最近访问的软衰减。但开源接口明确把部分 `timestamp`、`reference_date` 等时间能力标为平台能力，因此不能把托管版公开能力直接等同于当前 OSS 实现。

对“老余口述”的启示是：

- ADD-only 比“新值覆盖旧值”更适合回忆录；
- 同一件事的再次讲述可能是补充、视角变化或后续发展，不应默认当作重复；
- 语义、关键词和实体三路召回适合人物密集、表达多样的口述内容；
- 纯 ADD-only 也会积累碎片和近似重复，因此仍需要独立的跨会话整合与状态管理；
- “最近访问”可以影响召回排序，但不应删除不常被访问的人生材料。

主要来源：

- [Mem0 论文](https://arxiv.org/abs/2504.19413)
- [Mem0 2026 研究架构](https://mem0.ai/research)
- [当前主线提取和检索实现](https://github.com/mem0ai/mem0/blob/7e096155714cd67360f91cc8d82fbbb8bda3c903/mem0/memory/main.py)

### 2.4 Graphiti/Zep：带时间和来源的动态关系图

Graphiti/Zep 的数据模型最接近回忆录场景。其知识图包含三层：

1. **Episode 子图**：保存原始消息、文本或 JSON，是非破坏性的输入和来源层；
2. **Semantic Entity 子图**：保存从 episode 中提取并消歧后的人物、地点、组织等实体，以及实体之间的事实关系；
3. **Community 子图**：保存强关联实体群的高层摘要。

事实关系具有有效时间窗口。新信息与旧信息冲突时，旧事实可以被标记为失效，但仍保留历史，而不是物理删除。每条派生关系仍可回溯到产生它的 episode。

其查询组合以下信号：

- BM25 全文检索；
- 向量余弦相似度；
- 图上的 BFS 或节点距离；
- RRF、MMR、交叉编码器或其他重排方式。

Graphiti 还支持预定义 ontology 和随数据形成的 learned ontology。这说明“不想过度模板化”不等于完全没有类型，而可以先保留少量通用类型，再让具体人物和关系从内容中逐步涌现。

知识图本身不会自动保证事实正确。实体提取、消歧、时间解析和冲突判断仍可能依赖模型产生错误，因此图中的每条派生事实仍需要来源证据、认识状态和可纠正机制。

对“老余口述”的启示是：

- 必须区分“这次访谈记录到的内容”和“系统当前认为成立的长期事实”；
- 人生事件需要同时保存故事发生时间和讲述记录时间；
- 人物、地点、事件和关系应能从原始讲述增量生成；
- 旧说法失效或受到质疑时应保留历史和来源；
- 图结构适合跨人物、跨事件和跨时间段的多跳问题，但不必在第一阶段直接引入图数据库；关系数据库也可以先表达实体、关系、时间和来源。

主要来源（源码快照 `993e081a6d7948a0d8851c12a5fbdbeb49fed862`）：

- [Zep 时间知识图论文](https://arxiv.org/abs/2501.13956)
- [Graphiti 官方仓库](https://github.com/getzep/graphiti/tree/993e081a6d7948a0d8851c12a5fbdbeb49fed862)
- [Graphiti 混合检索配置](https://github.com/getzep/graphiti/blob/993e081a6d7948a0d8851c12a5fbdbeb49fed862/graphiti_core/search/search_config_recipes.py)

### 2.5 Letta/MemGPT：小型核心记忆与大型外部档案

MemGPT 最初借鉴操作系统分层内存，把有限的模型上下文看作快速内存，把大量外部资料看作需要按需调入的慢速内存。后续 Letta 曾以以下几层实现这一思想：

- 始终在上下文里的核心记忆块；
- 可检索的历史消息；
- 通过语义搜索按需读取的 archival memory。

当前 Letta 又将长期记忆演进为 Git 版本化的 MemFS：

- `system/` 下的少量文件始终注入系统提示词；
- 其他记忆文件默认不进入上下文；
- 文件树始终可见，文件名和目录充当导航；
- 需要时由 agent 使用普通文件搜索和读取工具下钻；
- 默认没有向量索引，可以额外安装关键词、语义或混合搜索模块；
- 每次记忆修改都通过 Git 留下版本历史。

对“老余口述”的启示是：

- AI 每次对话只需要一个很小的核心认知，不需要把全部人生记忆放进上下文；
- 核心认知可以包含讲述者身份、当前人生阶段、活跃人物、上次停留位置、互动边界和少量高优先级未完线索；
- 大量历史故事、人物细节和证据应按需检索；
- 记忆的修改历史本身很重要，可以支持回滚、用户纠正和审计；
- 不能完全依赖模型自行决定何时写入或搜索，关键提取和激活策略仍应由产品工作流约束。

### 2.6 LangGraph/LangMem：画像、记忆集合与后台整理的工程取舍

LangGraph 将短期记忆定义为 thread-scoped state，将长期记忆放在跨 thread 的 namespace store 中。它把长期记忆分为：

- semantic memory：事实和知识；
- episodic memory：经历或过去的操作序列；
- procedural memory：规则、提示词或处理方式。

对于用户事实，它对比了两种保存方式：

- **Profile**：持续修改一份 JSON 用户画像。读取方便、上下文完整，但画像变大后容易更新错误或丢失字段；
- **Collection**：保存多条范围较小的独立记忆。通常召回更好，也不容易因一次更新丢失大量信息，但去重、修改、删除、搜索和上下文组装更复杂。

LangMem 则提供两种写入时机：

- 在主对话 hot path 中由 agent 主动管理记忆，能够立即生效，但增加延迟并让模型同时承担对话和记忆决策；
- 在后台自动提取、整合和更新，不阻塞主对话，但需要明确触发频率和新记忆可见时机。

对“老余口述”的启示是：

- 不能只选 profile 或 collection，应组合“小型核心画像＋独立记忆集合”；
- 项目、用户和记忆种类必须用明确 namespace 或数据库外键隔离；
- 实时会话只维护工作记忆，长期记忆尽量在后台形成；
- 记忆写入策略和检索质量必须单独评测，框架本身不能保证提取正确。

主要来源：

- [LangGraph Memory Overview](https://docs.langchain.com/oss/python/concepts/memory)
- [LangGraph Store 与语义搜索](https://docs.langchain.com/oss/python/langgraph/add-memory)
- [LangMem](https://github.com/langchain-ai/langmem/tree/29cbe41e58528f92e9efa773c12e15c47be3808c)

### 2.7 OpenAI 长期个性化示例：候选记忆、全局记忆与注入优先级

OpenAI 的公开工程示例使用“状态＋自由记忆笔记”的组合，并提出一条完整生命周期：

1. 会话开始时注入结构化 profile 和经过整理的全局记忆；
2. 会话过程中把值得记录的内容写入 session memory，作为候选暂存区；
3. 会话结束后异步整合，把稳定候选提升到 global memory；
4. 整合阶段处理去重、冲突和遗忘；
5. 下一次会话继续复用更新后的状态。

该示例明确指出，整合是最敏感、最容易出错的阶段，可能造成：

- 过度裁剪导致重要信息丢失；
- 把噪音、推测或不可靠信号提升为长期事实；
- 长期积累矛盾和重复；
- 旧记忆过度影响当前用户意图。

它还建议：当前用户表达高于当前会话记忆，当前会话记忆高于全局默认；全局记忆只能作为建议，不能覆盖用户当下明确表达。

对“老余口述”的启示是：

- 当前讲述永远高于历史记忆；
- 当前会话中的临时要求不能自动修改长期偏好；
- 只有表现出持久性的内容才进入全局核心认知；
- 记忆注入要评测“是否过度影响”，而不只是“有没有召回”。

主要来源：

- [Context Engineering for Personalization](https://developers.openai.com/cookbook/examples/agents_sdk/context_personalization)

## 三、跨系统共同规律

### 3.1 原始历史、派生记忆与上下文摘要是三种不同数据

- 原始历史回答“用户当时实际说了什么”；
- 派生记忆回答“系统从历史中观察到了什么”；
- 上下文摘要回答“当前这次模型调用最需要知道什么”。

三者不能相互替代。上下文摘要可以被重新生成，派生记忆可以被纠正或失效，原始音频和文字证据必须长期保持可追溯。

### 3.2 两阶段处理比一次性生成全局记忆更可靠

多个系统都采用或推荐：

```text
当前会话/故事段落
  → 候选记忆提取
  → 跨会话去重、关联、冲突判断和提升
  → 核心记忆与可检索详细记忆
```

第一阶段关注“这次说了什么”，第二阶段关注“它与过去的认识是什么关系”。将两种任务塞进一次调用，容易让模型在没有召回完整历史的情况下过早覆盖旧结论。

### 3.3 高质量提取必须允许不产出

如果提取器被要求每次必须返回人物、事件、情绪和价值观，就会为了满足 schema 而推断不存在的内容。高精确率系统必须允许：

- 没有长期价值；
- 当前只有临时信息；
- 无法可靠消歧；
- 需要更多上下文；
- 只能记录为未确认候选。

### 3.4 “不过于模板化”不等于“完全无结构”

纯自由文本不利于来源追踪、冲突处理、检索过滤和评测；过度固定的人生模板又会忽略意外但重要的内容。较好的折中是：

> 外层元数据严格结构化，内层记忆内容允许自由表达。

外层至少规定来源、时间、状态、主体和证据；内层的故事意义、情绪、关系描述和重要细节可以由模型自由表达。

### 3.5 事实更新和回忆补充不是同一件事

“我现在住在上海”可以使以前的当前住址失效，但“那年冬天我第一次去上海”不会因为后来补充了同行者就变成无效事件。记忆整合必须区分：

- 完全重复；
- 同一事件的细节补充；
- 同一主题的后续发展；
- 当前状态变化；
- 明确纠正；
- 无法解释的矛盾；
- 不同人物或不同视角的并存叙述。

### 3.6 混合检索通常优于单一向量检索

- 关键词/全文检索擅长姓名、地名、称谓、方言和原话；
- 向量检索擅长同义表达和主题相似；
- 实体或图检索擅长人物关系与多跳信息；
- 时间过滤擅长当前状态和人生阶段；
- reranker 负责在候选集中结合当前问题重新排序。

只使用向量相似度，容易遗漏精确稀有词，也容易召回主题相似但人物或时间错误的记忆。

### 3.7 检索与激活必须是两个独立步骤

检索回答“哪些记忆可能相关”，激活回答“哪些内容应进入本次模型上下文，以及模型应如何看待它”。检索到的内容可能：

- 只是背景，不需要注入；
- 尚未确认，只能作为追问线索；
- 与当前表达冲突，应以当前表达为准；
- 涉及隐私，不应主动提起；
- 与当前故事相似但属于另一个人物，不应使用。

如果不记录检索候选、激活选择和最终使用情况，就无法判断一次错误是发生在提取、召回、重排、上下文组装还是模型回答阶段。

## 四、对“老余口述”的建议记忆分层

### 4.1 原始证据层

不可被 AI 静默改写，继续由现有后端数据库作为事实源：

- 原始音频文件；
- `VoiceUtterance`；
- ASR 原文、校正文和 `TranscriptVersion`；
- `TranscriptAlignment` 的文字区间与音频区间；
- 会话、消息、说话人和项目归属；
- 用户手工纠正及版本记录。

长期记忆、书稿和分享片段最终都应能回溯到这一层。

### 4.2 情节记忆层

保存“这一次讲述中出现了什么”，尽量接近原始叙述，而不是过早压缩成人物画像：

- 一次经历或一段故事；
- 相关人物、地点和时间范围；
- 重要情绪和态度；
- 值得保留的原话；
- 本段的叙事意义；
- 尚未讲完的线索；
- 可以自然继续追问的问题；
- 对应的证据区间。

这一层同时服务于访谈接续、故事正文生成和精彩片段发现。

### 4.3 长期认知层

从多个情节记忆中逐步形成项目级认识：

- 人物、别名和称谓；
- 地点、组织和重要物品；
- 人物关系；
- 人生事件与时间线；
- 可核对的事实断言；
- 重复出现的主题和价值观；
- 稳定的互动偏好；
- 用户明确设置的话题边界和隐私决定；
- 存在矛盾或尚未确认的说法。

这一层不应只保存一段总结，而应保留独立、可关联、可版本化的记忆记录。

### 4.4 激活视图层

根据当前会话临时组装，不成为新的事实源：

- 讲述者身份和 AI 交流方式；
- 当前正在讲的人生阶段或故事；
- 当前活跃人物及其关系；
- 上次停留位置；
- 最相关的少量历史事实；
- 值得继续但尚未完成的线索；
- 需要澄清的冲突；
- 本次不应主动触碰的话题。

激活视图类似“小型核心记忆”，其余大量记忆仍按需检索。

## 五、建议的数据语义

本节只描述语义需要，不直接决定物理表结构。

### 5.1 记忆内容

每条记忆应有自由表达的主体内容，同时具有少量稳定元数据：

- `kind`：人物信息、事件、关系、事实、偏好、未完线索等弱类型；
- `content`：自包含、可独立理解的自由文本；
- `subject` / `object`：可选实体引用；
- `recorded_at`：用户何时讲述；
- `valid_time`：故事或事实在用户人生中的发生/有效时间；
- `status`：候选、已确认、存在争议、已被纠正、已失效、已拒绝；
- `source_kind`：用户明确陈述、从上下文推断、助手生成或外部资料；
- `evidence_refs`：对应的 transcript、文字区间和音频区间；
- `related_memories`：重复、补充、延续、纠正、矛盾或替代关系；
- `extractor`：提取模型、提示词版本和任务版本；
- `created_at` / `updated_at`：系统记录时间。

### 5.2 不确定度

不要只保存模型自行给出的单一置信度。更可靠的是记录可验证信号：

- 是否为用户明确陈述；
- 是否存在直接原文和原声证据；
- ASR 和对齐质量；
- 时间表达是否明确；
- 人物是否成功消歧；
- 是否被用户多次独立提及；
- 是否被用户确认或纠正；
- 是否与已有记忆冲突。

最终置信状态可以由这些信号派生，而不是让模型用一个小数自证准确。

### 5.3 时间语义

至少区分：

- **讲述时间**：用户在什么时候说了这段话；
- **发生时间**：故事在什么时候发生；
- **有效时间**：一个状态从什么时候开始、到什么时候结束；
- **系统时间**：记忆何时提取、整合和失效。

对于“那年冬天”“我十六岁时”“后来第二年”之类表达，应保留原始模糊表达和推导后的时间范围，不能只留下一个看似精确但未经确认的日期。

### 5.4 冲突语义

新候选与旧记忆之间至少需要区分：

- `duplicate`：语义相同，没有新增价值；
- `adds_detail`：补充了同一事件的细节；
- `continues`：同一故事或关系的后续；
- `updates_current_state`：当前状态发生变化；
- `corrects`：用户明确纠正旧说法；
- `contradicts`：两条说法冲突但无法自动判断；
- `different_perspective`：同一事件的不同主体或不同视角。

除非用户明确删除原始素材，否则冲突处理应改变派生记忆的状态和关系，不物理删除原始证据。

## 六、建议的提取与整合流程

### 6.1 会话中的工作记忆

实时语音主链路只维护当前工作记忆，例如：

- 当前人物和代词指代；
- 当前故事主题；
- 最近已经问过的问题；
- 本次刚出现的待确认事实；
- 本次暂时不能打断的叙述线索。

工作记忆服务于低延迟跟进，不直接写成已确认长期事实。

### 6.2 会话结束后的候选提取

一次讲述结束或稳定空闲后，后台任务读取：

- 本次完整转写和必要的前序上下文；
- 当前人物/地点导航；
- 本次访谈模式和问题；
- 已有但仅限于去重、指代解析所需的少量相关记忆。

输出应包括：

- 情节记忆候选；
- 人物、地点、事件和关系候选；
- 时间表达及其不确定度；
- 未完线索和下一步问题候选；
- 每个候选的直接证据；
- 无产出原因。

### 6.3 独立的实体与时间解析

不要让一次 LLM 调用同时承担所有工作。人物消歧和时间解析可以作为后续独立阶段：

- “老王”“王师傅”“隔壁王叔”是否同一人；
- “县城”“老家县里”是否同一地点；
- “第二年春天”相对于哪一事件；
- “那时候我十六七岁”应映射为哪个模糊区间。

解析失败时保留候选和原始称谓，不强行合并。

### 6.4 跨会话整合

整合器检索相关旧记忆，对新候选执行：

1. 精确或近似去重；
2. 实体归一和别名连接；
3. 时间和关系补充；
4. 重复、补充、延续、更新、纠正或矛盾分类；
5. 更新未完线索和当前故事地图；
6. 只有高信号、稳定内容才提升到核心激活视图；
7. 保留所有证据和变更历史。

### 6.5 定期重建派生视图

人物导航、时间线、故事地图、核心记忆和向量索引都应能够从规范记忆和证据重新生成。这样可以在：

- 提取模型升级；
- 提示词调整；
- 用户纠正；
- 实体合并或拆分；
- 时间线重新判断；

之后安全重建，而不需要改写原始数据。

## 七、建议的检索与激活流程

### 7.1 查询理解

检索请求不只使用用户当前一句话，还应结合：

- 当前访谈模式；
- 当前故事和人生阶段；
- 已识别人物、地点和时间表达；
- 当前问题的目的：自然追问、事实核对、自动编辑、分享发现或成书审阅；
- 当前未完线索。

同一句“后来呢”几乎没有独立检索意义，必须结合活跃故事和人物才能形成有效查询。

### 7.2 候选召回

建议并行使用：

1. 全文/BM25：召回姓名、地点、称谓、方言和原话；
2. 向量语义：召回不同表达下的相似经历和主题；
3. 实体关系：从当前人物扩展到相关事件、地点和其他人物；
4. 时间过滤：优先当前人生阶段或问题指定区间；
5. 未完线索：优先与当前故事直接相关的开放问题。

### 7.3 融合与重排

可以先用 RRF 等确定性方法融合多路候选，再让 reranker 结合以下因素重排：

- 与当前问题的直接相关性；
- 人物和项目是否一致；
- 时间是否匹配；
- 是否已确认；
- 证据质量；
- 是否已经在当前会话使用；
- 是否可能导致重复提问；
- 是否涉及不可主动提起的隐私边界。

### 7.4 激活策略

激活上下文只放入少量真正有用的内容，并明确其认识状态：

- 已确认事实可以作为可靠背景；
- 未确认候选只能用于生成澄清问题；
- 矛盾记忆应提示模型不要擅自选边；
- 隐私敏感内容不能因为相关就自动提起；
- 当前用户表达高于所有历史记忆；
- 当前会话明确要求高于全局互动偏好。

对于低风险、高确定性的记忆，AI 可以自然接续；对于不确定或影响较大的内容，更适合使用“您上次好像提到……”这类可纠正表达。

### 7.5 记录检索与使用结果

每次记忆使用建议记录：

- 原始查询和查询目的；
- 各召回通道的候选和分数；
- 融合、重排后的结果；
- 实际注入上下文的记忆；
- 模型最终是否使用；
- 用户是否确认、忽略或纠正；
- 是否帮助避免重复问题或自然接续。

这些数据是后续评测和改进的基础，不应只保留最终回答。

## 八、评测建议

### 8.1 可借用的公共评测维度

LongMemEval 将长期记忆分为五类能力：

- 信息提取；
- 跨会话推理；
- 时间推理；
- 知识更新；
- 无充分证据时放弃回答。

LoCoMo 还覆盖超长多会话下的问答、事件总结和多模态对话。它们适合作为方法参考，但不能代替回忆录真实数据上的评测。

主要来源：

- [LongMemEval 论文](https://arxiv.org/abs/2410.10813)
- [LongMemEval 官方仓库](https://github.com/xiaowu0162/LongMemEval)
- [LoCoMo 论文](https://arxiv.org/abs/2402.17753)
- [LoCoMo 官方仓库](https://github.com/snap-research/locomo)

### 8.2 回忆录特有评测维度

#### 提取

- 记忆候选精确率和召回率；
- 人物、地点和事件归属准确率；
- 直接证据区间准确率；
- 用户陈述与模型推断的归因准确率；
- 时间表达和模糊区间准确率；
- 无价值内容的正确不提取率。

#### 整合

- 重复判断准确率；
- 补充、后续、更新、纠正和矛盾分类准确率；
- 人物别名合并与错误合并率；
- 是否错误覆盖原始记忆；
- 用户纠正后是否正确传播到派生视图。

#### 检索

- Recall@K、MRR 或 nDCG；
- 姓名、地点和方言等精确检索成功率；
- 跨人物、跨会话和跨时间多跳召回率；
- 无相关记忆时的空召回质量；
- 延迟和注入 token 数。

#### 激活

- 激活内容是否真正帮助当前任务；
- 记忆是否错误覆盖当前表达；
- 不确定记忆是否被错误表述为事实；
- 是否减少重复提问；
- 是否自然接续上次未完故事；
- 用户纠正率和用户对“AI 记得我”的主观信任。

#### 下游业务结果

- 自动编辑是否减少人物和时间不一致；
- 章节和全书是否保持事实一致；
- 下一阶段问题是否更具体且不重复；
- 精彩片段发现是否召回完整、有感染力且安全的故事段；
- 用户是否更愿意再次打开小程序继续讲述。

### 8.3 建议的首轮验证方式

从少量真实、脱敏的回忆录访谈开始建立人工标注集，至少包含：

- 单会话明确事实；
- 同一事件的多次补充；
- 人物别名和容易混淆的人物；
- 模糊时间和相对时间；
- 用户明确纠正；
- 两次说法存在冲突但无法判断；
- 应当拒绝形成长期记忆的闲聊或助手建议；
- 应自然接续的未完线索。

首轮至少比较以下基线：

1. 只使用最近若干条对话；
2. 只使用向量检索；
3. 全文检索加向量检索；
4. 分层记忆加实体、时间和谨慎激活。

早期目标应是证明新方案在不增加错误激活的前提下，能够减少重复提问、改善自然接续和提高事实一致性，而不是只追求“存了多少条记忆”。

## 九、建议的实施顺序

本文不直接确定实现范围，但根据调研结果，合理的演进顺序是：

1. **先建立证据化候选记忆**：从完整访谈后台提取自由文本候选，每条绑定 transcript/audio 证据，允许无产出；
2. **补齐状态与关系**：支持确认、争议、纠正、失效、重复、补充和矛盾，不自动覆盖旧证据；
3. **建立混合检索**：优先复用关系数据库和全文索引，再增加向量召回；
4. **建立小型激活视图**：围绕当前人物、故事、时间段和未完线索组装上下文；
5. **增加实体和时间整合**：逐步形成项目级人物导航、关系和人生时间线；
6. **服务自动编辑和精彩片段发现**：让记忆成为事实一致性、故事归类和候选发现的共同基础；
7. **基于真实评测演进**：有明确收益后再决定是否需要专门图数据库、复杂 reranker 或训练专用提取模型。

第一版不建议先做：

- 一份由 LLM 不断覆盖的总人生摘要；
- 只保存 embedding、不保存规范记忆和证据；
- 每句话实时写入长期记忆；
- 让新说法自动删除旧说法；
- 在没有评测集的情况下堆叠复杂知识图和多模型流水线；
- 把所有召回结果无差别注入每次语音对话。

## 十、下一阶段待讨论问题

1. 现有 `VoiceUtterance`、`TranscriptVersion`、`TranscriptAlignment`、消息和项目数据能否完整承担证据层；
2. 情节记忆应复用当前 `SectionMaterial`，还是需要独立于书稿结构的项目级 story/episode 模型；
3. 实体、关系、事实、事件和未完线索应采用哪些最小规范类型；
4. 用户确认应发生在每条事实、冲突出现时，还是通过低打扰的集中审阅完成；
5. 哪些核心记忆始终进入语音访谈上下文，哪些只能按需检索；
6. 现有数据库全文能力是否足够支持第一版，向量索引应采用什么可重建边界；
7. 记忆更新任务如何接入现有 `EditingJob`、后台任务 deadline、进度事件和失败恢复体系；
8. 如何从真实访谈建立首轮记忆提取、整合、检索和激活评测集。
